# 飞书任务跟进 Agent

把飞书群里「口头派的活」变成可追踪的任务。

群消息里的人话说得随意——「周五之前把报告发我」「这个你们俩分别跟一下」。这类指派说完就沉进聊天记录里，
没人记、没人催、没人验收。这个项目要解决的就是这一段：**从群消息里把任务捞出来，落到库里，盯到闭环**。

```
飞书群消息 → 识别候选 → 人工确认建单 → 状态流转 → 定时提醒 → 状态变更反馈
                                              ↑                    |
                                     点卡片按钮 / 群里说一句话 ←──┘
```

## 核心原则

**模型只做理解，不做决定。**

大模型只负责把一段人话读成结构化候选，输出必须过 Pydantic 校验；状态机、时间换算、权限判断、
通知投递全部由确定性代码执行。模型输出永远不直接写库、不发消息、不改状态。

**所有建单必须人工确认。**

模型读错了，代价是弹一张卡片让人点「忽略」；如果直接建单，代价是一条假任务混进别人的待办里，
几次之后所有人都不再信这个系统。

**宁可漏，不可错。**

尤其体现在反馈层：一句话读不出明确结论就当没看见，也不去猜。状态被悄悄改错比没改难查得多。

## 几个值得单独说的设计

### 1. 候选与正式任务分表

`task_candidate` 存模型读出来的东西，会 pending / confirmed / rejected / expired；
`task` 只存人工确认过的。分开是为了让正式任务表不被模型噪声污染——
排查「为什么这条任务不见了」时，不用在一堆废候选里翻。

### 2. 确认卡片必须扛住连点

飞书卡片回调 3 秒不响应就重推。用户连点两下、飞书重推一次，三个请求会同时到。
所以确认用**条件更新抢占**，靠 `rowcount` 判定谁抢到了：

```sql
UPDATE task_candidate SET status='confirmed' WHERE uid=? AND status='pending'
```

先查后写在并发下必然建出两张单。

### 3. 群卡不能按某一个人的权限裁剪

一张卡发到群里，几个人同时看。飞书没法给不同读者渲染不同按钮。
踩过的坑：群卡按负责人的权限过滤，结果待验收的任务在群里**一个按钮都没有**——
负责人没验收权，发起人明明能验收却看着卡片显示「你没有任何可执行的动作」，任务就这样卡死。

现在的规则：**群卡渲染状态允许的全部动作，点击时再按点击者身份校验**（value 带 `pub:1`，
点完仍返回公共视角）；私聊卡才按人裁剪。

### 4. 通知拆成「算 / 存 / 发」三层

- **算**：`plan_digests(now)` 纯函数，`now` 当参数传，测试能随便造假时间
- **存**：发件箱表，`dedupe_key` 唯一约束做幂等
- **发**：Worker 投递，失败重试，超时限放弃

直接调接口发的问题：发失败就丢了、定时任务重跑会重复发、一次网络抖动丢掉一整天。
这套东西等价于 Java 里的本地消息表 / 事务性发件箱。

日报和事件通知共用同一个发件箱，加一种通知只需要写「算」那一段。

### 5. 时间基准是消息时间，不是 `now()`

「明天下午三点」指的是**说这句话的时候**的明天。用处理时刻去算，补跑历史消息会全错。
只精确到日的表达默认取 18:00 并标记 `assumed=True`——那是系统补的，得让人看得出来。
算不出、指向过去、今天已过点，一律 `unresolved`，绝不返回一个假时间。

### 6. 反馈层只认回复

群里同时五件事在跑，凭空一句「做完了」猜错就改错任务。
所以只处理**回复派活那条消息**的反馈，且要挡住反话和问句：

| 输入 | 结果 | 为什么 |
|---|---|---|
| 做完了 | 提交验收 | — |
| 还没做完 | **不处理** | 读成完成会把任务推到待验收，然后没人验收，任务悄悄死掉 |
| 做完了吗 | **不处理** | 问句不是结论 |
| 一句话对应多条任务 | 回「请在卡片上点」 | 不猜 |

## 快速开始

### 1. 准备飞书自建应用

1. 开放平台创建**企业自建应用**，开启「机器人」能力
2. 权限：`feishu-permissions.json` 可批量导入（8 个 scope）
3. 事件订阅：`im.message.receive_v1`，订阅方式选 **使用长连接接收事件**
4. 回调配置：`card.action.trigger`（**这是独立页面，和事件订阅不是一回事**），同样选长连接
5. 创建版本并发布 → 把机器人拉进群

> 卡在「该应用尚未配置卡片回调」就是第 4 步没做。长连接模式下不需要公网地址、不需要自己验签。

### 2. 装依赖

```bat
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

### 3. 填配置

复制 `.env.example` 为 `.env`，至少填 `FEISHU_APP_ID` / `FEISHU_APP_SECRET` / `MODEL_*`。

有交互式脚本可以代劳，写完会当场发一次真实请求验证：

```bat
set_cred.bat     :: 飞书凭证
set_model.bat    :: 模型服务（DeepSeek / 通义 / 智谱 / Ollama / 自定义）
```

### 4. 跑起来

```bat
run.bat        :: 长连接主进程（收消息、发卡片）
worker.bat     :: 另一个窗口，定时提醒
```

## 环境上的坑（Windows）

- `.bat` 必须 **CRLF + GBK 编码 + `chcp 936`**，UTF-8 会让中文 echo 被 cmd 切分报「不是内部或外部命令」
- 跨盘要 `cd /d`；venv 绑死绝对路径，移动目录后删掉 `.venv` 重建
- **Clash 等系统代理会掐断到 `open.feishu.cn` 的 TLS**，典型报错
  `SSL: UNEXPECTED_EOF_WHILE_READING`。代码里已把飞书域名写进 `NO_PROXY`，
  自己新增入口时别忘了
- SQLite 的 `DATETIME` 不存时区，`TZAwareDateTime` 用带偏移的 ISO 字符串绕开
