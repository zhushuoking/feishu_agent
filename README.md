# 飞书任务跟进 Agent

把飞书群里「口头派的活」变成可追踪的任务。

群消息里的人话说得随意——「周五之前把报告发我」「这个你们俩分别跟一下」。这类指派说完就沉进聊天记录里，
没人记、没人催、没人验收。这个项目要解决的就是这一段：**从群消息里把任务捞出来，落到库里，盯到闭环**。

```
飞书群消息 → 识别候选 → 人工确认建单 → 状态流转 → 定时提醒 → 状态变更反馈
                                              ↑                    |
                                     点卡片按钮 / 群里说一句话 ←──┘
```

## 核心原则

**模型只做理解，不做决定。**

大模型只负责把一段人话读成结构化候选，输出必须过 Pydantic 校验；状态机、时间换算、权限判断、
通知投递全部由确定性代码执行。模型输出永远不直接写库、不发消息、不改状态。

**所有建单必须人工确认。**

模型读错了，代价是弹一张卡片让人点「忽略」；如果直接建单，代价是一条假任务混进别人的待办里，
几次之后所有人都不再信这个系统。

**宁可漏，不可错。**

尤其体现在反馈层：一句话读不出明确结论就当没看见，也不去猜。状态被悄悄改错比没改难查得多。

## 几个值得单独说的设计

### 1. 候选与正式任务分表

`task_candidate` 存模型读出来的东西，会 pending / confirmed / rejected / expired；
`task` 只存人工确认过的。分开是为了让正式任务表不被模型噪声污染——
排查「为什么这条任务不见了」时，不用在一堆废候选里翻。

### 2. 确认卡片必须扛住连点

飞书卡片回调 3 秒不响应就重推。用户连点两下、飞书重推一次，三个请求会同时到。
所以确认用**条件更新抢占**，靠 `rowcount` 判定谁抢到了：

```sql
UPDATE task_candidate SET status='confirmed' WHERE uid=? AND status='pending'
```

先查后写在并发下必然建出两张单。

### 3. 群卡不能按某一个人的权限裁剪

一张卡发到群里，几个人同时看。飞书没法给不同读者渲染不同按钮。
踩过的坑：群卡按负责人的权限过滤，结果待验收的任务在群里**一个按钮都没有**——
负责人没验收权，发起人明明能验收却看着卡片显示「你没有任何可执行的动作」，任务就这样卡死。

现在的规则：**群卡渲染状态允许的全部动作，点击时再按点击者身份校验**（value 带 `pub:1`，
点完仍返回公共视角）；私聊卡才按人裁剪。

### 4. 通知拆成「算 / 存 / 发」三层

- **算**：`plan_digests(now)` 纯函数，`now` 当参数传，测试能随便造假时间
- **存**：发件箱表，`dedupe_key` 唯一约束做幂等
- **发**：Worker 投递，失败重试，超时限放弃

直接调接口发的问题：发失败就丢了、定时任务重跑会重复发、一次网络抖动丢掉一整天。
这套东西等价于 Java 里的本地消息表 / 事务性发件箱。

日报和事件通知共用同一个发件箱，加一种通知只需要写「算」那一段。

### 5. 时间基准是消息时间，不是 `now()`

「明天下午三点」指的是**说这句话的时候**的明天。用处理时刻去算，补跑历史消息会全错。
只精确到日的表达默认取 18:00 并标记 `assumed=True`——那是系统补的，得让人看得出来。
算不出、指向过去、今天已过点，一律 `unresolved`，绝不返回一个假时间。

### 6. 反馈层只认回复

群里同时五件事在跑，凭空一句「做完了」猜错就改错任务。
所以只处理**回复派活消息或对应私聊任务卡**的反馈，且要挡住反话和问句。
确认建单、负责人处理、发起人验收、状态通知和提醒统一发送到各自与机器人的私聊。
私聊任务卡可直接点按钮，也可回复「开始做」「做完了」「验收通过」「验收不通过」。
每张卡根据任务 ID 关联状态，回复多任务会话中的一张卡只会操作该卡对应的任务。
每人每个任务复用一张操作卡，建单回执和状态通知更新原卡。
重要状态变化使用简短文字提醒。Worker 清理同一收件人的历史重复任务卡，超过撤回时限的副本会缩成简短合并提示。
私聊发送或卡片更新失败会通过现有发件箱重试。
待验收期间可继续回复任务卡补充完成说明，更新原验收卡。
取消和验收退回需要回复任务卡，例如「取消任务：需求调整」或「验收不通过：缺少测试数据」，
原因会保存到处理意见和状态日志。
群里发出的任务仍会进入识别流程，文字反馈的处理结果也通过机器人私聊发送。

示例反馈处理如下。

| 输入 | 结果 | 为什么 |
|---|---|---|
| 做完了 | 提交验收 | — |
| 还没做完 | **不处理** | 读成完成会把任务推到待验收，然后没人验收，任务悄悄死掉 |
| 做完了吗 | **不处理** | 问句不是结论 |
| 做完了吗。／搞定了没有／提交了没！ | **不处理** | 无问号或使用句号也按问句处理 |
| 如果完成了就发我／预计明天就完成了 | **不处理** | 条件和计划不代表任务已经完成 |
| 一句话对应多条任务 | 回「请在卡片上点」 | 不猜 |

## 快速开始

### 1. 准备飞书自建应用

1. 开放平台创建**企业自建应用**，开启「机器人」能力
2. 权限：`feishu-permissions.json` 可批量导入（8 个 scope）
3. 事件订阅：`im.message.receive_v1`，订阅方式选 **使用长连接接收事件**
4. 回调配置：`card.action.trigger`（**这是独立页面，和事件订阅不是一回事**），同样选长连接
5. 创建版本并发布 → 把机器人拉进群

> 卡在「该应用尚未配置卡片回调」就是第 4 步没做。长连接模式下不需要公网地址、不需要自己验签。

### 2. 装依赖

```bat
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

### 3. 填配置

复制 `.env.example` 为 `.env`，至少填 `FEISHU_APP_ID` / `FEISHU_APP_SECRET` / `MODEL_*`。

有交互式脚本可以代劳，写完会当场发一次真实请求验证：

```bat
set_cred.bat     :: 飞书凭证
set_model.bat    :: 模型服务（DeepSeek / 通义 / 智谱 / Ollama / 自定义）
```

### 4. 跑起来

启动前在 `.env` 中用 `FEISHU_ALLOWED_CHAT_IDS` 填写授权群的 `chat_id`，多个 ID 用英文逗号分隔。空名单不处理群消息。要临时停用授权群，将该群 ID 加入 `FEISHU_DISABLED_CHAT_IDS` 并重启消息接入进程。

候选的确认和忽略只对该群的发起人或已授权项目经理开放。项目经理用 `FEISHU_CHAT_MANAGER_BINDINGS` 配置，每项是一个 `chat_id:open_id`，多项用英文逗号分隔。缺任务内容、发起人或有效负责人时，确认操作会提示补充，候选保留。候选过期后重新发起。

本地执行 `show_db.py --confirm <候选编号前缀>` 时，先在当前终端设置本人的短期 `FEISHU_USER_ACCESS_TOKEN`。工具从飞书取得用户身份后执行与确认卡相同的建单校验。日常使用可直接点飞书确认卡。

正式任务使用同一份按群项目经理授权。项目经理可提交完成、解除阻塞、验收、退回和取消。技术管理员需另获业务角色授权。负责人即使兼任发起人或项目经理，也不能验收或退回自己的任务。

新任务默认由发起人验收。可在 `FEISHU_CHAT_REVIEWER_BINDINGS` 为各群配置默认验收人，格式为 `chat_id:open_id`，多个授权以英文逗号分隔。建单时保存验收人，后续改群默认值只影响新任务。当前也支持在本地确认命令追加 `--reviewer ou_xxx` 指定该任务验收人。候选卡内的验收人编辑界面随候选修改表单后续补齐。

提交完成时会通知有验收权的发起人和验收人，并去重；两者都为负责人时，通知该群其他有验收权的项目经理。完成审核通过后通知负责人。旧任务未保存独立验收人时，以发起人为默认验收人。

```bat
run.bat        :: 长连接主进程（收消息、发卡片）
worker.bat     :: 另一个窗口，定时提醒
```

## 环境上的坑（Windows）

- `.bat` 必须 **CRLF + GBK 编码 + `chcp 936`**，UTF-8 会让中文 echo 被 cmd 切分报「不是内部或外部命令」
- 跨盘要 `cd /d`；venv 绑死绝对路径，移动目录后删掉 `.venv` 重建
- **Clash 等系统代理会掐断到 `open.feishu.cn` 的 TLS**，典型报错
  `SSL: UNEXPECTED_EOF_WHILE_READING`。代码里已把飞书域名写进 `NO_PROXY`，
  自己新增入口时别忘了
- SQLite 的 `DATETIME` 不存时区，`TZAwareDateTime` 用带偏移的 ISO 字符串绕开

## 待补充任务与人工补齐

确认建单时缺少交付物或截止时间，任务进入「待补充」。此状态展示缺失字段，
不计算逾期，也不进入普通日报、到期或逾期催办。发起人、负责人、验收人或项目经理
可以在机器人私聊回复对应任务卡，按下方格式提供信息。

```text
补充信息
交付物：联调测试报告
截止时间：明天18点前
```

支持分次补充，字段齐全后转为「待开始」，原卡随状态更新。时间无法解析时会提示重新填写，
跨群、越权、过期版本或对已完整任务的直接改期会被拒绝。完整任务的变更需经变更流程处理。
命令行也支持 `taskctl.py supplement <任务编号> --deliverable "报告" --deadline "明天18点前"`，
执行前仍需飞书验证操作者身份。

正式待补充任务每两个工作日最多提醒一次，由 `TASK_INFO_REMINDER_ENABLED` 控制。
历史待开始任务若缺负责人、交付物或截止时间，启动升级时会转入待补充，并记录版本及状态流水。
待开始任务可直接报阻塞或提交验收，操作仍按角色校验。

日报仅在工作日规划。免打扰时段不占用通知的补发时限，恢复后按最新任务状态复查。
提醒节流取实际最近一次成功投递时间。缺失字段补齐后，此前因条件不满足而跳过且从未发送的
提醒可以重新规划，已发送的相同业务键继续去重。

## 个人日历同步

建单后直接在负责人、发起人和指定验收人的个人主日历创建任务日程，每人每任务
保留一个副本。此流程使用各自授权的用户身份，不添加日程参与人。
完成、取消和改期继续同步到对应副本。用户撤销授权或授权失效时保留任务，
记录同步失败，等待重新授权后补偿。

首次连接按以下步骤配置。

1. 在飞书开放平台开通并发布用户身份权限 `auth:user.id:read`、`calendar:calendar`、
   `calendar:calendar:readonly`、`offline_access`。可从 `feishu-permissions.json` 核对用户身份权限。
2. 在应用安全设置中登记 OAuth 回调地址，默认开发地址为
   `http://127.0.0.1:8766/calendar/callback`，并允许刷新用户凭证。
3. 启动主程序和 Worker。主程序在个人日历模式下启动授权回调服务。
   朱硕和诸葛分别在与机器人的私聊发送「连接日历」，使用各自账号完成授权。
4. Worker 自动补齐待同步任务。后续建单直接写入个人日历。

`CALENDAR_SYNC_MODE=personal` 启用个人日历模式，当前默认配置为 `application`。`CALENDAR_AUTH_BASE_URL` 控制授权服务的对外地址。
本机地址适合同一台电脑上的开发联调，跨电脑使用时需配置可访问的 HTTPS 地址与回调代理，
`CALENDAR_AUTH_HOST` 控制本机监听地址。

访问凭证使用 AES-GCM 加密保存在任务库，密钥默认保存为任务库路径加 `.calendar.key`，
已由 `*.key` 排除提交。可用 `CALENDAR_TOKEN_KEY_FILE` 指定受控目录。
恢复数据库时需同时恢复对应密钥。离线凭证在到期前自动刷新，授权失效时用户重新连接。
回调校验一次性 state、有效期和实际登录账号，HTTP 访问日志关闭以保护授权码。

既有邀请模式保留为 `CALENDAR_SYNC_MODE=application`。
旧任务切换到个人模式后，所有目标个人副本写入成功才清理原应用日程。
`calendar_sync.py --list` 查看任务级状态，`--task <uid> --apply` 立即补同步。
每个账号的副本和错误记录保存在 `personal_calendar_event`。

授权和续期依据飞书的[用户访问凭证说明](https://open.feishu.cn/document/server-docs/api-call-guide/calling-process/get-access-token)
与[用户凭证刷新接口](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/refresh-user-access-token-v3)。
