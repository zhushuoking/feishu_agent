# 11 月 21 日飞书任务 Agent 开发清单

## 今日目标

发起人点击「确认建单」且任务成功入库后，机器人在原派发消息下回复一条回执，负责人照常收到任务卡。示例文案为「已建单｜提交联调测试报告｜负责人：诸葛」。

## 1. 开发

- [ ] **从建单成功分支触发。** 在 [card_action.py](../card_action.py) 的 `process()` 中找到 `ACTION_CONFIRM` 分支。沿用 [repo.py](../repo.py) 的 `confirm_candidate()` 抢占逻辑，仅在返回新任务时安排回复。连点、并发回调和飞书重推都应复用这一判断。
- [ ] **回复原消息。** 使用候选记录的 `message_id`，在 [feishu_api.py](../feishu_api.py) 封装回复调用。文案取正式任务标题和负责人，避免展示原始用户 ID；多人负责时列出所有负责人。原消息 ID 缺失时跳过回复并记录原因。
- [ ] **在后台发送。** 按钮回调沿用现有的成功提示和卡片更新逻辑，及时返回。让原消息回复和现有负责人任务卡投递各自独立处理失败，任一发送失败都不影响另一项。
- [ ] **记录失败。** 飞书返回失败或抛出异常时，保留已经创建的任务，日志记下任务 ID、原消息 ID 和失败原因。忽略候选、候选过期时不发送回执。

## 2. 自动化测试

测试里替换飞书发送调用，避免发出真实消息。可在 [建单与卡片回调测试](../tests/test_day9.py) 中补充断言。

| 场景 | 通过标准 |
| --- | --- |
| 正常确认 | 创建 1 条任务，安排 1 次原消息回复和 1 次负责人任务卡投递；回复目标等于候选的原消息 ID |
| 连点、重推或并发确认 | 同一个候选只产生 1 条任务和 1 条回执 |
| 忽略或过期 | 任务、回执、负责人任务卡均不产生 |
| 回复失败 | 任务仍可查询，负责人任务卡仍会尝试发送，日志可定位失败 |
| 原消息 ID 缺失 | 正常建单并投递负责人任务卡，记录跳过回复的原因 |

- [ ] 先跑建单相关测试，再从项目根目录运行下方命令执行全量测试。
- [ ] 确认全量通过，并记下最终通过项数。

```powershell

```
