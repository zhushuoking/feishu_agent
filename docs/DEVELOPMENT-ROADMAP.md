# 飞书任务跟进 Agent 设计差距与开发路线

对照基线为《飞书任务跟进 Agent 详细设计说明书》V1.0，2026 年 11 月 15 日开发评审稿。现状按 2026 年 11 月 20 日本地工作区核对，包含尚未提交的建单回执和候选补充提醒。既有验收记录显示，真实飞书群的双账号闭环、历史卡同步、到期和逾期提醒、原消息回执已实测。最新一次全量自动化测试为 237 项通过。候选补充提醒仅完成本地验证，运行中的 Worker 未载入该改动。 [既有验收记录](ACCEPTANCE.md)

当前可在测试群验证主要流程，距离首期试点仍缺权限边界、完整建单与变更流程、可恢复的事件和通知、周报审批及部署验收。下一轮先补群白名单、候选授权和建单必填校验。此前的 11 月 21 日清单保留作为单项开发记录，后续排期以本路线为准。

## 二、重新排定的开发顺序

沿用设计的开发、综合验收和两周试点结构，按退出条件推进。测试群继续用于联调，生产开关在对应阶段验收通过后开启。

### 阶段 1　群接入和建单权限

1. 增加群配置及停用开关。未配置或已停用的群在调用模型、拉取上下文和写任务前返回，仅记录必要的过滤结果。补消息类型、无 @ 非回复和自身消息初筛。
2. 在业务入口统一校验候选群、操作人、候选有效期、任务内容、发起人及至少一名负责人，再做条件更新。确认、忽略、卡片和本地工具都经同一套规则。隔离历史无负责人任务，逐条补齐或人工处置。
3. 明确并实现按群项目经理、可配置验收人和管理员权限边界。候选无权点击时不返回任务详情。同步收紧敏感日志并验证测试与生产配置隔离。
4. **退出条件**：两个群交叉验证，未授权群不进入模型、明示无权的人不能确认或忽略、过期任务和缺负责人的候选不能建单。已有正常建单和双账号验收继续通过。

### 阶段 2　数据库迁移和可靠性底座

1. 建立 PostgreSQL 和 Alembic，先在隔离环境试迁。合并事件存储口径，迁移候选、任务、参与人、版本、卡片及发件箱，核对计数、关联、时区和幂等键。
2. 事件接入增加持久处理任务，记录处理中、可重试和人工处置状态。把任务变更、审计及通知意图放入同一事务。回执、负责人卡和历史卡更新逐步改为可追踪的后台投递。
3. 补下一次重试时间、限流与永久失败分类、发送前复查、健康检查及人工重试入口。保留开发长连接，测试与生产可按设计选用长连接或 Webhook。
4. **退出条件**：已验证 PostgreSQL 迁移、失败注入和恢复。进程在事件登记或事务提交后中断，重启可续处理且不重复建单或发过时通知。

### 阶段 3　建单补充、反馈与授权变更

1. 补候选修改、多子任务确认、主负责人和任务编号。缺交付物或截止时间时按规则生成正式 `NEEDS_INFO`，从卡片补齐后转待开始，保留变更前后值和来源。
2. 增加消息索引与进展记录，反馈优先使用同群回复关系和编号，其次用限定候选集的语义评分。以设计阈值起步，低于 70 分不关联，70–89 分让人选择，90 分以上且无冲突时可自动关联。所有写动作再检权限和版本。
3. 实现延期、取消和换人的申请、批准、拒绝及通知。延期拒绝保留原期限，批准后重新计算提醒。完善验收卡、退回原因及重复提交更新原卡。
4. **退出条件**：跑通缺字段补齐、同消息多任务、歧义反馈、越权选择、延期和换人审批的飞书验收。模型识别到延期、取消或换人时无法直接修改任务事实。

### 阶段 4　通知策略和每周汇总

1. 按群配置工作日、日提醒时间和免打扰策略，补阻塞汇总、主负责人到期提醒、待验收提醒，以及确认人／负责人每两个工作日最多一次的正式待补充提醒。单独保留候选到期前提醒的配置和去重口径。
2. 每周一 09:30 按群保存统计快照，包含上周完成、当前逾期、本周到期、阻塞、待补充。仅项目经理可从私聊预览确认发群，按群和 ISO 周去重。任务事实由数据库统计。
3. **退出条件**：验证跨周、空报表、免打扰、否决或重复确认、Worker 重启补扫。无项目经理授权时不会发群。

### 阶段 5　上线准备和两周试点

1. 补齐 FastAPI 管理接口、Compose、环境隔离、结构化日志、心跳、告警、留存清理及加密备份。演练一键停群、回滚和恢复。
2. 用至少 200 条固定脱敏标注样例做回归。设计口径包括明确任务召回率与候选精确率均至少 90%、确认后的负责人及交付物准确率至少 95%、反馈关联准确率至少 90%、Schema 合法率至少 99%。用 20 群、日 5000 条消息、1000 活跃任务、日 300 通知作为容量验证参考。
3. 在审批确定的 2–3 个群依次开启 L0 影子运行、L1 人工确认、L2 单聊提醒、L3 完整试点。两周记录误建单、漏跟踪、推送成功率和人工催办耗时。推广前核验事件处理成功率至少 99.5%、通知成功率至少 99%、关键操作审计留存率 100%，跨群泄露为 0。
4. **退出条件**：设计 §13.7、§16.7、§17.3 的安全、业务及上线门槛通过。留有回滚演练、业务基线对照和验收记录。

## 三、开发用口径与待确认事项

**2026-11-22 阶段 1 进度。** 群消息入口白名单及候选审批已通过真实验收。正式任务的按群项目经理、独立验收人、禁止负责人自验收和技术管理员审批隔离已实现，本地全量 269 项通过。验收人可通过群默认配置或已验证身份的本地建单命令指定。候选卡内的修改表单、主负责人和正式任务角色的三账号飞书验收待完成。实际结果见[验收记录](ACCEPTANCE.md)。

- **负责人缺失**：§3.3 明确要求无负责人不得建单，§7.1 又把缺负责人列入正式 `NEEDS_INFO` 示例。路线采用 §3.3 的建单校验，缺负责人先留在候选阶段，正式 `NEEDS_INFO` 用于交付物或期限待补充。上线前请业务评审确认这一口径。
- **确认权限**：优先依据 §6.1.1 和 §7.4，由消息发起人或项目经理确认。负责人可建议修改。系统管理员只做技术配置。验证独立验收人规则与自派任务的验收安排。
- **补充提醒**：把 §7.1 的候选到期提醒和 §12.3 的正式任务补充提醒分别实现和验收。现有「满一小时提醒一次」属于当前候选规则，设计未指定这个时点。
- **试点准备**：由项目管理部确认群与项目经理名单，IT 和信息安全确认飞书权限、模型服务与留存策略。设计建议原文 90 天、模型报文 30 天，实际值以审批为准。
- **范围**：附件内容识别、自动建单和外部系统集成按 §18.4 留到后续。多维表格是 §2.2 可选视图，并排在 §18.4 扩展项，首期以数据库台账为准。

### 自动完善补充记录

按 §3.3、§7.1–7.2、§12.3 补齐正式 `NEEDS_INFO` 状态及人工补齐入口。
确认后缺交付物或截止时间时进入待补充，私聊回复原任务卡或经身份验证的 CLI 可分次补齐，
