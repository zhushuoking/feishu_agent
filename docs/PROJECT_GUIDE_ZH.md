# 飞书任务跟进 Agent 项目文件与业务流程详解

更新日期：2026 年 11 月 23 日。

这个项目把飞书授权群里的自然语言指派，转成经过人工确认、能够跟进和验收的任务。它同时管理任务状态、机器人私聊操作卡、提醒消息和可选的日历副本。理解代码时应抓住三个核心：模型只负责理解，正式任务由人确认，业务变更由状态机和权限规则控制。

本文按当前代码整理。已有 `ARCHITECTURE.md` 和 `CODE_WALKTHROUGH.md` 包含开发早期规则，例如允许自验收、较少的状态和数据库表；与当前实现不一致时，以代码及本文列出的现行规则为准。

## 一 项目整体结构

项目采用 Python 平铺模块结构，没有拆成多个服务包。主要有两个常驻进程，它们共享 SQLite 数据库。

| 运行单元 | 入口 | 主要工作 |
|---|---|---|
| 消息接入进程 | `main.py`，由 `run.bat` 启动 | 建立飞书长连接，接收消息和卡片回调，识别候选，处理交互 |
| 后台 Worker | `worker.py`，由 `worker.bat` 启动 | 定时生成提醒，投递发件箱，清理过期候选，补偿卡片与日历同步 |
| 日历授权服务 | `calendar_auth.start_server()` | 个人日历模式启用时，由主进程启动 OAuth 授权回调服务 |
| 本地工具 | `show_db.py`、`taskctl.py` 等 | 查看数据、诊断配置、辅助确认和操作任务 |

主流程可按下面的顺序理解：

授权群消息 → 内部消息对象 → 去重 → 优先尝试反馈处理 → 模型提取候选 → 规则解析截止时间 → 保存候选 → 私聊确认 → 正式任务 → 操作与验收 → 通知及同步。

其中数据库中的正式任务是业务依据。卡片、日历和飞书任务中心中的对象都是展示或外部副本，不应绕过业务仓储直接反向修改任务。

## 二 业务代码逐文件说明

### 2.1 接入与识别

| 文件 | 功能与关键入口 | 上下游关系 |
|---|---|---|
| `main.py` | 总装入口，`main()` 初始化并注册事件，`on_message()` 串起消息处理流程 | 调用消息解析、去重、反馈、识别、仓储和发送接口 |
| `models.py` | 定义 `Mention`、`MessageCommand`，`parse_event()` 将飞书 SDK 对象转成统一内部对象 | 提取发送者、群、消息时间、回复关系和真实提及身份；后续模块不必重复解析原始事件 |
| `store.py` | 维护事件收件表，`is_new_event()` 判断事件是否第一次处理 | 在进入业务逻辑前拦截飞书重复推送 |
| `prompts.py` | 保存系统提示词与版本，`build_user_prompt()` 拼接消息上下文 | 将消息时间、提及名单、发送者和正文交给模型 |
| `llm.py` | 封装 OpenAI 兼容模型接口、配置读取、JSON 提取和错误处理 | 识别层通过 `chat_json()` 获取结构化内容；模块还提供文本调用接口 |
| `schemas.py` | 用 Pydantic 定义 `ExtractedTask` 与 `TaskRecognition` | 校验模型输出字段、类型和约束，避免任意 JSON 直接进入业务 |
| `detector.py` | `detect()` 组织模型调用、Schema 校验、负责人校验、优先级校验和时间解析 | 返回候选结构，不负责正式建单和发送消息 |
| `deadline.py` | 将中文时间表达转为带时区的截止时间 | `parse_deadline()` 处理单个表达，`apply_to_tasks()` 将结果补到识别任务中 |

负责人验证尤其关键：模型返回的负责人标识必须存在于当前消息的真实 mentions 中，不能仅凭模型生成一个 `open_id`。紧急优先级也要有当前原文内能够核验的肯定证据，否则回退普通优先级。

时间解析以消息发送时间为基准。例如昨天发出的“明天交”，今天才处理，仍应按昨天的“明天”换算。只给日期而没有具体时刻时，可按规则补默认时间并保留规则信息；模糊或无法可靠解析的表达不能伪造截止时间。

### 2.2 数据和业务规则

| 文件 | 功能与关键入口 |
|---|---|
| `db.py` | 管理数据库路径、连接、事务和升级；`session_scope()` 正常提交、异常回滚；`init_db()` 建表并补充历史结构 |
| `models_db.py` | 定义 ORM 表、状态常量、关系与派生属性，例如负责人列表、有效验收人、缺失信息和逾期判断 |
| `repo.py` | 主要业务仓储，负责候选保存和确认、任务查询、状态变更、信息补充、卡片登记、通知队列及日历同步记录 |
| `state_machine.py` | 定义哪些状态允许哪些动作；`resolve_action()` 根据当前状态和动作得到目标状态 |
| `permissions.py` | 管理授权群、群项目经理、默认验收人及角色动作矩阵；`can()` 判断某个人能否执行动作 |

`repo.py` 是最重要的业务中心。理解项目时，优先读 `save_candidates()`、`confirm_candidate()`、`transition_task()` 和 `supplement_task()`。状态机只回答“这一步能不能走”，权限模块只回答“这个人能不能走”，仓储把它们和事务、版本检查及日志组合起来。

数据库采用 WAL 模式并打开外键检查。时间使用 `TZAwareDateTime` 按带偏移的 ISO 字符串保存，避免 SQLite 普通日期字段丢失时区。当前迁移由 `create_all()` 和 `_upgrade()` 补列完成，还没有完整 Alembic 迁移体系。

### 2.3 卡片与交互

| 文件 | 功能与关键入口 |
|---|---|
| `cards.py` | 构造候选确认卡、任务卡、日报卡和过期提示等 JSON；主要入口为 `build_candidate_card()`、`build_task_card()` |
| `card_action.py` | 接收卡片点击，提取候选或任务标识、操作人和版本；调用仓储并返回 toast 与更新后的卡片 |
| `feishu_api.py` | 封装飞书消息发送、卡片更新、撤回、确认卡推送和任务卡复用；`upsert_task_card()` 用于更新或创建个人操作卡 |
| `feedback.py` | 识别回复中的开始、阻塞、完成、验收、取消和补充信息；根据回复消息关联具体任务，再调用业务仓储 |
| `card_sync.py` | 将历史卡片刷新到最新任务版本，合并或清理重复卡片；既支持异步触发，也支持 Worker 定期补偿 |

卡片渲染与点击校验是两回事。私聊卡可以按收件人的角色裁剪按钮；公共卡则展示状态允许的动作，实际点击时仍按操作者身份校验。不能因为按钮显示出来，就认为点击者已经获得业务权限。

当前交互重点是机器人私聊：每人每任务尽量复用一张操作卡。状态变化更新原卡，必要时再发简短文字提醒，避免每次变化都产生一张长期保留的旧卡。

### 2.4 通知与外部同步

| 文件 | 功能与关键入口 |
|---|---|
| `events.py` | 状态变更后的即时通知，`recipients()` 决定收件人，`on_transition()` 写入发件箱，`flush_async()` 触发后台投递 |
| `notify.py` | 计算日报、到期、逾期和信息待补充提醒；维护工作日、免打扰、节流和去重键规则 |
| `worker.py` | `tick()` 执行一轮后台任务，`drain_outbox()` 抢占并发送通知；失败记录及重试由仓储配合处理 |
| `calendar_api.py` | 封装飞书日历 HTTP 请求、凭证、日历查询、日程创建、更新、删除和参与人操作 |
| `calendar_sync.py` | 将任务转换为日程，管理应用日历与个人日历两种模式，支持异步触发和定时补偿 |
| `calendar_auth.py` | 个人日历 OAuth 授权、一次性 state 校验、用户身份核对、凭证加密保存与刷新 |
| `native_task.py` | 可选地在确认建单后创建飞书原生任务，设置负责人、关注人、描述和截止时间 |

`native_task.py` 与日历同步不是一回事。前者写入飞书任务中心，由 `FEISHU_NATIVE_TASK_ENABLED` 控制；当前实现是后台线程创建并有限重试，没有日历模块那样完整的本地映射和持续状态同步机制，不能理解为双向任务同步。

## 三 一条群消息如何变成正式任务

以“@小王 明天下午三点前提交联调报告”为例，完整流程如下。

1. 飞书通过长连接把事件交给 `main.on_message()`。
2. `models.parse_event()` 得到群 ID、真实负责人身份、发送时间和正文，替换飞书提及占位符。
3. 主流程检查消息类型与群授权。未授权或已停用的群直接忽略，机器人消息也会过滤。
4. `store.is_new_event()` 登记事件。相同事件再次推送时不再进入识别。
5. 优先交给 `feedback.apply_feedback()` 判断是否是已有任务反馈，防止把“做完了”识别为新任务。
6. 普通群消息进入 `detector.detect()`。模型提取标题、交付物、截止原文、负责人、证据等信息，Pydantic 校验后执行负责人和优先级后置检查。
7. `deadline.py` 按消息发送时刻解释“明天下午三点”，补充解析结果。
8. `repo.save_candidates()` 保存待确认候选。同一消息内的任务序号与消息标识形成去重约束。
9. 自动推卡开关打开时，向发起人私聊发送确认卡。此时只产生候选，还没有正式任务。
10. 用户点确认，`card_action.py` 调用 `repo.confirm_candidate()`，检查群授权、操作者、候选有效期和必要字段。
11. 条件更新只允许一个请求取得仍为 pending 的候选，随后在事务中创建任务、负责人关系和第一条状态日志。重复点击不会重复建单。
12. 卡片回调尽快返回。负责人卡片、建单回执、可选原生任务和日历同步放到后台执行。

确认权限属于来源群的发起人或已授权项目经理。任务内容、发起人或有效负责人缺失时，不能完成确认。若只是交付物或截止时间缺失，可以建立正式任务，但进入“待补充”，而不是直接作为正常待办催办。

验收人优先采用确认时显式指定值，其次采用群默认验收人，否则使用发起人。验收人写入具体任务，之后修改群默认配置不会自动替换已经创建任务的验收人。

## 四 状态与权限如何协同

### 4.1 当前状态流转

| 当前状态 | 允许的后续状态与含义 |
|---|---|
| 待补充 `NEEDS_INFO` | 补齐后进入待开始，或取消 |
| 待开始 `TODO` | 开始处理、报阻塞、直接提交验收或取消 |
| 进行中 `IN_PROGRESS` | 报阻塞、提交验收或取消 |
| 阻塞 `BLOCKED` | 解除阻塞回进行中、提交验收或取消 |
| 待验收 `PENDING_ACCEPTANCE` | 通过后完成、退回进行中、取消；也可保持待验收并补充完成说明 |
| 已完成 `DONE` | 终态，不再流转 |
| 已取消 `CANCELLED` | 终态，不再流转 |

“提交验收”与“已完成”不同。负责人声明做完，只把任务交到审核环节；具有验收资格的其他人通过后才算完成。逾期是根据截止时间和任务状态计算的属性，不是独立业务状态。

### 4.2 当前动作权限

| 动作 | 允许角色 |
|---|---|
| 补充信息 | 负责人、发起人、验收人、群项目经理 |
| 开始处理、报阻塞 | 负责人 |
| 解除阻塞 | 负责人、发起人、群项目经理 |
| 提交验收 | 负责人、群项目经理 |
| 验收通过、验收退回 | 发起人、验收人、群项目经理，但负责人身份优先触发禁止自验收 |
| 取消任务 | 发起人、群项目经理 |

技术管理员身份不自动获得这些业务权限。一个人可以有多个角色，但只要同时是该任务负责人，就不能验收或退回自己的任务，即使他同时是发起人、验收人或项目经理。

### 4.3 状态修改内部步骤

`repo.transition_task()` 先读取任务并检查群授权，再检查调用方携带的版本、状态动作和操作者权限。取消与退回必须填写原因；提交完成时可保存完成说明，待验收时也可继续补充说明。

真正更新采用带版本条件的 UPDATE：只有数据库版本仍与刚读取的版本一致，才更新状态并递增版本。这样两个人同时点击旧卡，只有一个操作成功。成功后同一事务写状态流水，事务完成后再触发事件通知、卡片刷新和日历同步。

这里存在一个需要理解的可靠性边界：任务修改与事件通知入队是分开的事务。外部接口失败不会回滚任务；但如果任务提交后、通知入队前进程崩溃，或入队本身失败，不能仅靠发件箱保证该通知一定存在。发件箱保证的是已经成功入队的消息可继续处理。

## 五 文字反馈与信息补充

`feedback.py` 通过回复关系定位任务。群里回复原始指派消息，或者私聊回复对应任务卡，都能提供关联线索；一句没有上下文的“做完了”不会任意匹配任务。若一条回复关联多个任务且无法唯一确定，系统要求用户在具体卡片操作。

识别主要依赖规则。问句、否定、条件和未来计划需要过滤，例如“还没做完”“做完了吗”“预计明天完成”不能当作提交验收。换一种表达未必能识别，当前没有模型兜底来随意推断状态。

待补充任务可回复对应任务卡填写“补充信息”，并提供“交付物：联调测试报告”“截止时间：明天18点前”等字段。`supplement_task()` 执行参与人、来源群、任务状态、版本和时间校验，支持分次补齐；字段满足要求后进入待开始。

此入口用于补足缺失内容，不是对已完整任务任意改期。取消和退回可使用“取消任务：需求调整”“验收不通过：缺少测试数据”，原因会进入任务意见和状态流水。

## 六 后台提醒和卡片如何保持一致

Worker 默认每 60 秒执行一轮 `tick()`：使过期候选失效，规划日报及各类提醒，写入通知发件箱，投递到期通知，补偿卡片同步，最后检查日历同步。

通知采用“计算、入队、发送”的分工。`notify.py` 读取任务并计算通知，`repo.enqueue_notification()` 通过唯一业务键去重，Worker 抢占待发记录后执行接口调用。失败会记录错误并按规则重试，超过限制进入失败或跳过状态。

日报在工作日按时段规划；到期与逾期提醒各有开关。逾期和正式任务待补充提醒按工作日节流，并参考实际成功投递时间。待补充任务不进入普通日报、到期和逾期催办。候选创建满一小时仍待确认且缺信息时，也有单独的候选提醒。

免打扰期间延迟投递。恢复投递时，会按最新任务状态重新核验：例如任务已完成、群已停用或提醒已不适用，就不能继续发送旧催办。日报也会重新计算，避免把早已失效的快照直接推给用户。

`task_card` 保存任务和已发消息的关系、收件人视角及同步版本。状态变化后，`card_sync.py` 重新渲染落后卡片；多余副本优先撤回，不能撤回时可改成合并提示。Worker 定期补偿异步更新失败的记录。历史上未登记消息标识的卡片无法直接靠此机制找回。

## 七 日历同步与授权流程

应用模式 `application` 将任务映射到应用可操作的日历日程，并处理参与人；个人模式 `personal` 使用每个用户自己的授权，在负责人、发起人及验收人的个人主日历创建各自副本，不通过添加参与人来实现。

个人模式下，用户私聊机器人发送“连接日历”，主进程生成授权链接。用户登录并授权后，回调检查一次性 state、有效期和实际账号，保存个人日历信息及加密凭证。后续调用使用用户身份，访问凭证到期时通过离线凭证刷新。

凭证采用 AES-GCM 加密，密钥文件与数据库需要一起保管和恢复。撤销授权或凭证失效时，任务仍然有效，只记录日历同步失败，重新授权后再补偿。

任务创建、状态变化和截止变更都有同步入口，Worker 的 `reconcile()` 负责重试与补齐。完成时更新日程展示，取消时删除对应日程。由应用模式迁移到个人模式时，先确认目标个人副本全部写入，再清理旧应用日程，避免先删后建造成缺失。

## 八 数据库中每张表保存什么

当前源码定义 10 张 ORM 业务表，另外 `store.py` 管理 1 张事件去重表。

| 表 | 保存内容 | 作用 |
|---|---|---|
| `event_inbox` | 已接收事件 ID、消息和群等 | 拦截事件重推，不代表业务处理一定成功 |
| `task_candidate` | 原始消息、模型提取内容、时间解析、证据、缺失字段和候选状态 | 隔离模型噪声，保留人工确认前的数据 |
| `task` | 正式任务、状态、版本、创建者、验收人、截止与处理意见 | 任务业务事实来源 |
| `task_assignee` | 任务与负责人的关系 | 支持多负责人及角色记录 |
| `task_status_log` | 状态前后值、操作者、原因及时间 | 审计业务过程 |
| `task_card` | 任务对应的已发卡片、收件人视角、同步版本及失败情况 | 更新旧卡、选择主操作卡、清理重复卡 |
| `notify_outbox` | 通知类型、唯一业务键、收件人、载荷、投递状态及重试信息 | 可靠投递已入队通知 |
| `task_calendar_event` | 任务级应用日程映射、幂等请求及同步状态 | 应用模式同步和任务级同步协调 |
| `calendar_account` | 个人日历账号与加密凭证 | 用户身份日历访问 |
| `calendar_oauth_state` | 授权请求的临时 state | 防止授权回调串号或重复使用 |
| `personal_calendar_event` | 每任务每用户的个人日程副本及同步错误 | 独立跟踪多人的同步结果 |

几种 ID 不要混淆：`event_id` 用于事件去重，`message_id` 用于回复和更新卡片，`candidate.uid` 标识候选，`task.uid` 标识正式任务，`open_id` 标识用户，`chat_id` 标识来源群。日历自身还有 `calendar_id` 与 `event_id`，这里的日历事件 ID 与消息事件 ID 属于不同接口语义。

## 十一 常见问题的定位路径

| 现象 | 优先检查 |
|---|---|
| 群里派活没有反应 | `main.py` 的授权过滤、机器人过滤、事件去重，再看 `detector.py` 与模型配置 |
| 有候选但没确认卡 | 自动推卡开关、`feishu_api.push_confirm_card()`、发起人私聊可达性和发件箱 |
| 点击确认不建单 | 候选是否过期、操作者是否有权、任务内容和负责人是否有效 |
| 负责人不能验收 | 当前规则禁止自验收，需其他有权限人员处理 |
| 卡片点击提示已更新 | 卡片版本落后或存在并发操作，检查任务版本与 `card_sync.py` |
| 做完了没有改状态 | 是否回复正确消息、是否关联多任务、是否被否定或问句规则拦截、是否有提交权限 |
| 取消或退回失败 | 是否提供原因，使用回复任务卡的完整语句 |
| 没有提醒 | Worker 是否运行、数据库是否一致、免打扰/工作日/开关、任务是否待补充或待验收、发件箱状态 |
| 日历没有副本 | 同步开关与模式、用户授权和权限、映射表错误及 Worker 补偿情况 |
| 旧卡仍显示旧状态 | 是否有登记消息 ID、同步是否失败或已退休、是否为无法找回的早期卡片 |

事件去重发生在识别和落库之前。如果后面的模型调用或业务处理失败，再次重推同一事件也可能被判为重复。当前主流程会打印识别失败日志，但没有自动实现注释中提到的完整人工失败队列；排查时不能把“事件已登记”等同于“候选已成功创建”。

## 十二 修改功能时从哪里入手

| 想调整的行为 | 需要一起检查的模块 |
|---|---|
| 提高任务识别准确率 | `prompts.py`、`schemas.py`、`detector.py` 及识别回归 |
| 支持新的中文日期说法 | `deadline.py` 及时间解析测试 |
| 增加状态或动作 | `models_db.py`、`state_machine.py`、`permissions.py`、`cards.py`、`repo.py` 和通知逻辑 |
| 调整审批或验收角色 | `permissions.py`、候选确认及状态变更测试 |
| 改卡片显示 | `cards.py`，同时核对私聊视角和公共视角 |
| 支持新的反馈语句 | `feedback.py`，重点增加否定、疑问和歧义场景 |
| 增加提醒类型 | `notify.py` 或 `events.py`、Worker 规划与发送前复核、业务去重键 |
| 修改日历行为 | `calendar_sync.py`；接口和授权问题分别看 `calendar_api.py`、`calendar_auth.py` |
| 增加数据库字段 | `models_db.py` 与 `db._upgrade()`，兼顾新库及历史库 |

推荐阅读顺序为 `models.py` → `schemas.py` → `models_db.py` → `state_machine.py` → `permissions.py` → `repo.py` 核心写操作 → `main.py` → 卡片和反馈 → Worker → 日历。先理解数据对象与规则，再看总装代码，更容易看清各模块之间的边界。
