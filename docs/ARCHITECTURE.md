# 飞书任务跟进 Agent — 当前文件说明（截至 2026-11-17，Day 13）

主链路已经闭环：

```
飞书群消息 → 识别 → 人工确认建单 → 状态流转 → 定时提醒 → 状态变更反馈
                                                        ↑
                                            点卡片按钮 / 群里说一句话
```

## 一、业务代码：跑数据流的五条

| 文件 | 职责 | 删了会怎样 |
|---|---|---|
| `main.py` | 程序入口。建立长连接、收事件、按「过滤机器人 → 去重 → 状态反馈 → 识别 → 时间解析 → 候选落库」顺序调用 | 整个程序不会启动 |
| `models.py` | 把飞书事件转成内部 `MessageCommand`。剥掉 `@_user_1` 占位符、提取 open_id、时间转 Asia/Shanghai | 下游拿到的还是飞书的原始结构，每处代码都要自己解析一遍 |
| `store.py` | 事件去重。`event_inbox` 表 + `is_new_event()` | 飞书重推时会出现重复建单（文档 14.3 不允许） |
| `detector.py` | 识别编排。拼提示词 → 调模型 → Schema 校验 → 后置校验负责人 → 回填截止时间 | 没有识别能力，只能打印原文 |
| `deadline.py` | 时间解析。「本周五前」→ 带时区的 `deadline_at`。基准是消息时间，算不出来就返回 unresolved | 截止时间永远是 null，Day 12 的提醒功能无从下手 |

## 一之二、数据层（Day 8 新增，四张业务表）

| 文件 | 职责 |
|---|---|
| `db.py` | 引擎 + 会话 + `TZAwareDateTime`。**SQLite 存时间会丢时区**，这里用带偏移的 ISO 字符串绕开；每条连接 PRAGMA 开外键和 WAL |
| `models_db.py` | 四张表：`task_candidate`（候选）/ `task`（正式任务）/ `task_assignee`（负责人）/ `task_status_log`（状态流水）。逾期用 `is_overdue` 派生，不落库 |
| `repo.py` | 仓储层。`save_candidates` / `confirm_candidate` / `reject_candidate` / `expire_candidates` / `list_*`。业务代码不直接写 SQL |

为什么候选和任务分开：候选是「模型觉得像任务」，会被忽略、会 72 小时过期、会被驳回；任务才是人确认过要跟进的东西。混在一张表里，正式任务表迟早全是垃圾数据。

## 一之三、卡片层（Day 9 新增，Day 11 扩展）

| 文件 | 职责 |
|---|---|
| `cards.py` | 卡片 JSON 构造，**纯函数不联网**。候选卡（确认/忽略）、已建单回执、已忽略、已失效，以及 Day 11 加的 **任务卡**（`build_task_card`，按钮按「状态 × 权限 × 看卡的人」动态渲染） |
| `feishu_api.py` | 发消息的薄封装。所有函数**都不抛异常**，失败返回 None：卡片发不出去是「通知失败」，不是「业务流程失败」。`push_confirm_card` 私聊优先回落群；`push_task_card` 按负责人逐个私聊 |
| `card_action.py` | 卡片回调处理。`process()` 是纯逻辑（只碰本地库），`handle()` 是飞书适配层。带 `cid` 的是候选动作，带 `tid` 的是任务状态动作 |

回调的三条硬约束（写在 `card_action.py` 顶部）：
1. **3 秒内必须响应**，所以回调里不调模型、不发消息（推任务卡放 daemon 线程）
2. **重推 = 并发**，靠 `repo` 里的条件更新抢占，第二次拿 None
3. **不能抛异常**，最外层统一兜底，永远返回一张能看懂的卡片

Day 11 的两个关键设计：
- **按钮是算出来的，不是写死的**：`next_actions(状态)` ∩ `permissions.can(谁)`。所以负责人看不到「取消任务」（那是发起人的权利）
- **按钮 value 带 `ver`（乐观锁）**：卡片上的 `v3` 点下去时如果你已经改到 `v4`，系统拒绝而不是覆盖，并把卡片刷成最新

**群卡和私聊卡不是一回事**（这条是真实事故换来的）：

| | 怎么渲染按钮 | 为什么 |
|---|---|---|
| 私聊卡（传 `viewer_open_id`） | 按这个人的权限过滤 | 一对一，他看不到自己点不了的按钮 |
| 群卡（不传 viewer） | 渲染**状态允许的全部动作**，`value` 带 `pub:1`，点击时再校验身份 | 一张卡多人看，飞书没法按读者渲染不同按钮 |

事故经过：群里的待验收任务按负责人一个人的权限渲染 → 一个按钮都没有 → 片上写「你在这条任务上没有可执行的动作」→ 发起人明明能验收，却以为自己也点不了 → **任务卡死**。

配套规则：`pub:1` 的卡点完之后**必须还公共卡**，不能变成点击者的私人视角，否则发起人点完一次，卡片就只剩负责人的按钮了。

## 一之四、状态与权限（Day 10 新增）

| 文件 | 职责 |
|---|---|
| `state_machine.py` | 状态转移表 + 动作解析。`TRANSITIONS` 一张表定死什么状态能去哪；终态先挡（`DONE`/`CANCELLED` 任何动作为不合法）；`resolve_action` 失败时告诉人「这个动作只能在××状态用」 |
| `permissions.py` | 三个角色（负责人 / 发起人 / 管理员）+ 动作权限矩阵。管理员名单从 `.env` 的 `AGENT_ADMIN_OPEN_IDS` 读，改权限不用改代码 |
| `taskctl.py` | 状态机 CLI：`list` / `show` / `start` / `block` / `unblock` / `submit` / `accept` / `reject` / `cancel`。不传 `--as` 就按 `AGENT_DEFAULT_OPERATOR` → 第一个负责人 |

两条容易写错的规则（都踩过）：
- **「没负责人时发起人代行」的兜底不能写成 `if not roles`** —— 发起人自己一定有 creator 角色，`roles` 永远非空，那样写兜底等于永远不生效
- **发起人 = 负责人时允许自验收，但流水里要留「自验收」** —— 硬挡会让自派的任务永远走不完，偷偷放行又等于没有验收

## 一之五、通知层（Day 12 新增）

| 文件 | 职责 |
|---|---|
| `notify.py` | 日报**生成**逻辑，纯函数。`plan_digests(now)` 扫库 → 按负责人分组 → 分三堆（已逾期 / 今天到期 / 明天到期）。`now` 是参数不是全局，所以测试能随便造假时间 |
| `worker.py` | 定时 Worker。每 60 秒 tick 一次：候选过期 → 生成日报入队 → 发送到点通知。`--once` 跑一轮、`--now` 假装时间、`--dry-run` 只算不发 |
| `models_db.NotificationOutbox` | 通知发件箱表。`dedupe_key` 唯一约束做幂等，`status` 走 pending→sent / failed / skipped |
| `cards.build_digest_card` | 日报卡片。三段分组，每条任务最多一个按钮（点一下就能推进状态，复用 Day 11 的 `tid`+`ver`） |

**为什么要有发件箱**，这是 Day 12 唯一需要想明白的东西：

直接调接口发的问题有三个：发失败就丢了（提醒的价值全在准时送到）；定时任务重跑会重复发；发送和业务耦合，一次网络抖动丢掉一整天。

所以拆三层：**算**（纯函数）→ **存**（发件箱，唯一键幂等）→ **发**（Worker，失败重试）。这个模式在 Java 里对应「先落库再投递」，和本地消息表是同一套思路。

四条时间规则，都是踩过的：

| 规则 | 值 | 为什么 |
|---|---|---|
| 日报时段 | 09:00 之后才生成 | 不加这个判断，Worker 半夜启动会立刻把当天日报推出去 |
| 免打扰 | 22:00–08:00 不发 | **延后**，不是丢弃：`scheduled_at` 不动，08:00 后自动捡起来 |
| 补发时限 | 超过 6 小时放弃 | 早上 9 点的「今天要交」，下午 4 点才发出去等于骂人 |
| 日报只走私聊 | 不回落群聊 | 确认卡片私聊失败会回落群（怕任务丢），但日报是个人待办，发群里没意义 |

`dedupe_key = DIGEST:{日期}:{open_id}` —— 一人一天一条。**不带 chat_id**：一个人在三个群里都有任务，该收一条汇总，不是三条各说各的。聚合维度是「人」。

## 一之六、事件通知与反馈层（Day 13 新增）

Day 12 只解决了「到点了提醒你」。还差两件事：**别人动了你的任务，你要立刻知道**；**你不用去点卡片，说一句就行**。

| 文件 | 职责 |
|---|---|
| `events.py` | 状态变更的即时通知。谁动了任务 → 该告诉谁 → 渲染私聊卡 → 写发件箱。`flush_async()` 起后台线程立刻发，不占卡片回调的 3 秒 |
| `feedback.py` | 把群里的一句话读成动作。`classify()` 纯规则，`resolve_tasks()` 靠回复关系定位任务，`apply_feedback()` 做预演后落库 |
| `main.py` | 反馈层插在「去重之后、任务识别之前」——顺序反了的话，「做完了」会被模型当成一条新任务建出来 |

**日报和事件通知的分工**，别混：

| | 触发方式 | 收件人 | 去重键 |
|---|---|---|---|
| 日报 | 每天 09:00 按时间扫 | 有任务到期的负责人 | `DIGEST:{日期}:{open_id}` |
| 事件通知 | 有人点了按钮/说了句话 | 该知道这件事的人 | `EVENT:{任务}:{动作}:{版本}:{open_id}` |

两者共用同一个发件箱、同一套重试和放弃规则 —— 这就是当初把「算/存/发」拆开的好处：加一种通知只需要写「算」这一段。

**收件人按动作定，不按状态定**（状态是结果，动作才是原因）：

| 动作 | 告诉谁 | 为什么 |
|---|---|---|
| 提交验收 | 发起人 | 轮到他验收了，不告诉他任务就停在这儿 |
| 验收通过 | 负责人 | 他要知道自己这活儿结没结 |
| 验收打回 | 负责人 | 要返工，得立刻知道，还得看到打回原因 |
| 报阻塞 | 发起人 | 阻塞往往要发起人去协调资源 |
| 取消 | 负责人 | 别再做了 |
| 开始处理 | **不发** | 他自己点的，通知他自己纯属噪音 |

还有一条：**收件人等于操作者时一律不发**。自己给自己派活、自己提交验收，再推一条「你提交了验收」给自己，就是纯噪音。

**反馈层的四条硬规矩**（每条都对应一种真实的错法）：

| 规矩 | 不做会怎样 |
|---|---|
| 只认「回复原消息」 | 群里同时五件事在跑，凭空一句「做完了」猜错就改错任务。代价不对等：让人多点一下，比改错一条便宜 |
| 反话必须挡住 | 「还没做完」「没搞定」被读成完成 → 任务被推到待验收 → 没人验收，任务悄悄死掉 |
| 问句不算结论 | 「做完了吗？」不是「做完了」 |
| 一句话对应多条任务就不猜 | 先用状态机和权限各预演一遍，只有唯一能成的那条才动手，否则回一句「请在卡片上点」 |

规则识别不出来就当没看见，继续走原来的任务识别流程 —— **宁可漏，不可错**。状态被悄悄改错，比没改更难查。
